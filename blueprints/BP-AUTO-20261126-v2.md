# BP-AUTO-20261126-v2 补充：异常自动打回返工，不经用户转手

- 日期：2026-11-26 CST
- 决策：用户明确不要一条条复制粘贴转手。像卡2假阳性这类问题，必须由本地巡检自己发现、自己打回返工，只有超限或判断不了才报用户。
- 关系：本文件是 BP-AUTO-20261126-v1 的补充，与 v1 一起执行；冲突时以本文件为准。

## 异常自动处置（巡检模型层打开，但只在异常时）

巡检脚本层每 10 分钟继续做确定性检查（零模型成本）：卡状态变化、声明产出存在且非空、卡超时、返工轮次、状态矛盾。无异常静默记录。

发现异常时，按下面顺序自动处置，不等用户转手：

1. **假阳性完成**（卡 done 但声明产出不存在/为空，如卡2这次）：脚本直接判定异常，不需要模型。自动把该蓝图状态记为 stopped/false_done，在 .state 写明证据；自动新建一张返工卡（blocked），assignee 换执行型角色（禁止 cc-review 当执行者，禁止原产出角色自审），卡正文写明失败原因和“你是执行者，必须写出声明产出文件”。返工卡走 v1 的估算+额度内放行规则。
2. **产出路径不对/内容明显跑题/卡卡住超时**：调 ikun 一次判断处置（打回重做/换角色/升级报用户）。单次上限 21000 词元，去重键 = 卡号+异常类型，24h 冷却，每轮最多 1 次模型调用。ikun 只给处置建议，建卡/放行仍走脚本和看板规则，不让模型直接改文件。
3. **返工计数**：同一蓝图自动返工最多 3 轮。第 3 轮仍失败：停下，不再自动重试，记 .state 并按关键事件通知用户（通道未定前写报告文件到 reports/ 并推回仓库）。
4. **判断不了的大改动**（要改源文件、改分工、改包装器以外代码、超预算）：不自动处置，停下报用户。

## 与判产漏洞的关系

BP-302-CONT-v4 第一步的判产修复是前置：声明产出不存在就不许判 produced。修好后，卡2这类假阳性在判产环节就被拦下，不会进 done；本补充是第二道防线，万一仍出现 done 无产出，巡检自动打回返工。

## 记录与通知

- 每次自动处置写 `.state/flow_state.json`：异常类型、处置动作、返工轮次、模型调用消耗。
- 日常自动处置成功不打扰用户；只有返工超 3 轮、正式任务最终完成或失败、巡检停了、超限停下，才算关键事件通知。

## 禁止

- 不让模型层每轮巡检都调；无异常零模型调用。
- 不自动改源文件、不自动改分工、不自动回滚提交（如 8879026 仍留用户定）。
- 不碰 config.env / engine.py / 桌面会话，不贴密钥值。

## 停下条件

同一异常 24h 内重复触发模型判断；返工卡重复建卡；.state 与看板矛盾；自动处置后产出仍为空且已到 3 轮。任一发生，关自动放行开关，写明证据并停下。
